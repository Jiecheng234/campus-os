# Feature Specification: 支付宝支付基础设施（T02）

**Created**: 2026-10-19
**Status**: Draft
**Input**: User description: "【T02 · 支付基础设施】Feature dir: harmony/specs/payment-alipay/。目标：提供电费/校园卡/体育共用的支付宝外跳与支付后回读基础设施。范围：payCode → 支付宝 URL/Deep Link 构建；openLink/startAbility 外跳；返回 App 后刷新余额/记录；失败可读、可重试；不伪造支付成功。非目标：各子系统的具体充值/下单 UI（T11/T12/T13）。验收：URL 构建可验证；真实设备能打开支付宝；返回后页面能刷新；异常路径有可读文案；日志无凭据。"

## Overview

为电费、校园卡、体育三个校园子系统提供一套共用的支付宝支付基础设施：把子系统服务端返回的支付码转换为可验证的支付宝 Deep Link，负责在用户确认后外跳支付宝，并在用户返回 CampusOS 时发出一次性的“支付回读”信号，供页面刷新余额、流水或订单记录。

本特性只交付可复用能力与诊断手段，不实现电费充值、校园卡充值或体育下单/退订的具体业务 UI。任何外跳结果只表示“已请求打开支付宝”或“返回了 CampusOS”，**不得表示支付成功**；支付结果必须由子系统回读余额/记录后自行判断。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从 payCode 构建可验证的支付宝链接 (Priority: P1)

子系统服务拿到服务端返回的支付码后，调用共用基础设施生成支付宝 Deep Link；构建规则必须与 RN 基线一致，且对空值、空白、控制字符和会破坏 URL 结构的字符给出明确拒绝，而不是生成一个不可用的链接。

**Why this priority**: 链接构建是外跳的前提，也是唯一可以脱离设备稳定验证的核心逻辑；三个子系统必须共用同一规则，避免各写一份产生偏差。

**Independent Test**: 用已知支付码构建链接，逐字符比对 RN 基线；用空串、空白串、控制字符、包含 URL 分隔符的串验证拒绝；用完整二维码 URL 验证末段提取。全程不需要网络或设备。

**Acceptance Scenarios**:

1. **Given** 子系统提供合法支付码，**When** 请求构建支付宝链接，**Then** 返回与 RN 基线结构一致的 Deep Link，且不发起任何网络请求
2. **Given** 支付码为空、仅空白、含控制字符或含会破坏 URL 结构的字符，**When** 请求构建，**Then** 返回“支付码无效”的可读错误，不返回可外跳的链接
3. **Given** 输入是完整的支付宝二维码 URL（含查询参数或末尾斜杠），**When** 提取支付码，**Then** 得到最后一个路径段，查询参数与片段被去除
4. **Given** 同一合法支付码被重复构建，**When** 多次调用，**Then** 结果完全一致（确定性），便于自检与回归

---

### User Story 2 - 从 CampusOS 外跳支付宝并在失败时可重试 (Priority: P1)

用户在子系统页面确认支付后，CampusOS 应能打开设备上的支付宝；若设备未安装支付宝、系统不允许该链接或外跳调用失败，用户应看到可读提示并可以重试，而不是停留在无响应状态或看到“支付成功”。

**Why this priority**: 这是用户可感知的主路径；没有可靠外跳，支付基础设施没有实际价值。失败可读与可重试是本特性的硬性验收项。

**Independent Test**: 在已安装支付宝的真机上通过调试自检入口触发外跳，确认支付宝被打开；在未安装支付宝的设备上触发同一入口，确认出现“未安装支付宝”的可读提示且应用不崩溃；恢复安装后重试成功。

**Acceptance Scenarios**:

1. **Given** 设备可访问支付宝且支付码合法，**When** 用户触发外跳，**Then** 支付宝被打开，CampusOS 记录一条待回读状态；界面只提示“已请求打开支付宝”，不提示支付成功
2. **Given** 设备未安装支付宝或目标链接不可访问，**When** 用户触发外跳，**Then** 返回“未检测到支付宝”的可读结果，提供重试入口，应用不崩溃，待回读状态被清除
3. **Given** 外跳接口返回错误（系统限制、链接不可用等），**When** 用户触发外跳，**Then** 返回“打开支付宝失败”的可读结果并允许重试，不泄露支付码或原始异常文本
4. **Given** 用户打开支付宝后取消支付并返回，**When** CampusOS 回到前台，**Then** 不产生任何“支付成功”结论；页面可刷新并展示“未确认支付结果”的提示

---

### User Story 3 - 返回 App 后收到一次性的支付回读信号 (Priority: P2)

用户从支付宝返回 CampusOS 后，发起支付的页面应收到一次回读信号，以便刷新余额、流水或订单记录；没有待回读状态、状态已过期或应用进程已重启时，不得误触发。

**Why this priority**: 回读是支付闭环的另一半，直接决定“返回后页面能刷新”的验收；同时必须避免把“返回”误当成“支付成功”。

**Independent Test**: 注入一条待回读状态后模拟应用回到前台，订阅方应收到恰好一次事件；无待回读状态时回到前台不触发；待回读状态超过有效期后回到前台不触发；重启应用后不补发陈旧事件。

**Acceptance Scenarios**:

1. **Given** 存在有效期内的待回读状态，**When** 应用从后台回到前台，**Then** 所有订阅方收到恰好一次回读事件，事件包含子系统标识、金额（若提供）和离开时长，随后状态被清除
2. **Given** 不存在待回读状态，**When** 应用回到前台（包括普通切后台再回来），**Then** 不发出回读事件
3. **Given** 待回读状态已超过有效期（30 分钟），**When** 应用回到前台，**Then** 不发出回读事件，并清除该状态
4. **Given** 应用在支付宝期间被系统终止，**When** 用户重新启动 CampusOS，**Then** 不补发陈旧回读事件；页面按正常加载流程刷新数据
5. **Given** 用户短时间内连续发起两次支付，**When** 第一次返回后再返回，**Then** 只有最新一次待回读状态生效，不产生重复或错配事件

---

### User Story 4 - 可诊断、可自检且日志不含凭据 (Priority: P3)

开发者与验证者需要一个仅调试构建可见的支付通道自检入口，用来确认支付宝是否可访问、测试 Deep Link 能否打开支付宝、返回事件是否触发；同时任何日志都不得出现支付码、二维码 URL、Cookie、学号或其它凭据。

**Why this priority**: 真实设备外跳无法靠纯构建验证；没有诊断入口就无法闭合“真实设备能打开支付宝”的验收。日志脱敏是安全底线。

**Independent Test**: 在 debug 构建中打开设置页的支付自检入口，分别验证“探测安装状态”“打开测试链接”“返回后收到回读提示”；用日志检索确认无支付码/二维码 URL；在 release 构建中确认该入口不可见。

**Acceptance Scenarios**:

1. **Given** debug 构建，**When** 用户进入设置页，**Then** 可见“支付通道自检”入口；release 构建不显示该入口
2. **Given** 点击“探测支付宝”，**When** 设备已安装/未安装支付宝，**Then** 分别显示“支付宝可用”/“未检测到支付宝”，不崩溃
3. **Given** 点击“打开支付宝测试链接”，**When** 设备可访问支付宝，**Then** 支付宝被打开，并明确提示“此操作不会发起支付”；返回后自检入口显示回读事件已触发
4. **Given** 完成一次外跳与返回，**When** 检索应用日志，**Then** 日志只包含子系统、状态码和耗时，不包含支付码、二维码 URL、金额明文、Cookie、学号或 API Key
5. **Given** 应用启动，**When** 支付自检运行，**Then** 链接构建与提取用例输出 PASS/FAIL，且不阻塞首页加载

---

### Edge Cases

- 支付码来自完整二维码 URL、带末尾斜杠、带查询参数或片段时，应正确提取末段；无法提取时返回“支付码无效”。
- 支付码包含 `&`、`?`、`#`、`/`、`%`、空白或控制字符时，应拒绝构建，避免生成可被注入或截断的链接。
- 设备未安装支付宝、支付宝被禁用、系统不允许该 scheme 或外跳接口返回错误时，均应有可读结果与重试路径，不得崩溃。
- 用户在支付宝内取消支付、直接返回、或支付宝停留在后台后再次切换回来时，不得推断支付成功。
- 应用在支付宝期间被系统终止、被用户上滑清除或发生崩溃时，不得在下次启动补发陈旧回读事件。
- 普通切后台再回来、从其它应用返回、首次启动进入前台时，不应误触发支付回读事件。
- 连续发起多次支付时，只保留最新待回读状态；旧状态不得覆盖新状态或在稍后误触发。
- 调试自检入口在 release 构建中必须不可见、不可通过正常导航到达。
- 支付基础设施本身不得发起余额/流水查询；回读由各子系统页面在收到信号后自行执行。
- 日志、错误提示、自检输出中不得出现支付码、二维码 URL、Cookie、学号、API Key 或金额明文。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供三个子系统共用的支付宝 Deep Link 构建能力，输入为服务端返回的支付码，输出为可外跳的链接。
- **FR-002**: 构建结果 MUST 与 RN 基线保持一致：`alipayqr://platformapi/startapp?saId=10000007&qrcode=` 前缀 + URL 编码后的 `https://qr.alipay.com/` + 支付码。
- **FR-003**: 系统 MUST 在构建前校验支付码：去除首尾空白后不得为空；长度不得超过 256；不得包含空白、控制字符、`&`、`?`、`#`、`/`、`%` 等会破坏 URL 结构的字符。
- **FR-004**: 系统 MUST 支持从完整二维码 URL 或裸支付码中提取末段支付码；查询参数与片段必须被去除。
- **FR-005**: 系统 MUST 在外跳前检查设备是否能访问支付宝；不可访问时 MUST 返回“未安装/不可访问”的可读结果，不得直接抛出未处理异常。
- **FR-006**: 系统 MUST 通过系统推荐的外部链接打开能力发起外跳；外跳成功只表示“已请求打开支付宝”，不得返回或展示“支付成功”。
- **FR-007**: 系统 MUST 在发起外跳前记录一条待回读状态，包含子系统标识、金额（调用方可选提供）、发起时间和有效期；外跳失败时 MUST 清除该状态。
- **FR-008**: 系统 MUST 在应用回到前台时检查待回读状态；存在且未过期时 MUST 向订阅方发出恰好一次回读事件，随后清除状态。
- **FR-009**: 待回读状态 MUST 仅在内存中保存，不得持久化；进程终止后不得补发陈旧事件。
- **FR-010**: 待回读状态的有效期 MUST 为 30 分钟；过期状态 MUST 被静默清除且不触发事件。
- **FR-011**: 系统 MUST 提供订阅/取消订阅回读事件的接口；同一事件不得重复投递给同一订阅方。
- **FR-012**: 系统 MUST 保证“无待回读状态”时的普通前台恢复不触发回读事件。
- **FR-013**: 系统 MUST 对连续多次支付采用“最新状态覆盖旧状态”的语义；旧状态不得在后续前台恢复时触发。
- **FR-014**: 服务层 MUST 返回稳定的状态码/错误码与 i18n 文案键，不得硬编码中文；页面负责本地化展示。
- **FR-015**: 系统 MUST 提供“未安装支付宝”“支付码无效”“打开支付宝失败”“未确认支付结果”等可读文案键，供 T11/T12/T13 复用。
- **FR-016**: 日志 MUST 只记录子系统、状态码、错误码和耗时；MUST NOT 记录支付码、二维码 URL、金额明文、Cookie、学号或 API Key。
- **FR-017**: 系统 MUST 提供仅 debug 构建可见的支付通道自检入口：可探测支付宝可访问性、打开测试 Deep Link、观察返回事件；release 构建 MUST 隐藏该入口。
- **FR-018**: 系统 MUST 提供可复现的链接构建/提取自检，输出 PASS/FAIL；自检 MUST NOT 发起真实支付、修改业务数据或阻塞首页加载。
- **FR-019**: 支付基础设施 MUST NOT 实现电费/校园卡/体育的具体充值或下单 UI，也 MUST NOT 代替子系统判断支付结果。
- **FR-020**: 外跳被用户取消、返回或超时后，系统 MUST NOT 自行把订单标记为已支付；子系统必须通过回读余额/流水/订单自行确认。

### Key Entities *(include if feature involves data)*

- **支付意图**：一次外跳的上下文，包含子系统标识、金额（可选）、发起时间、有效期；仅存在于内存。
- **链接构建结果**：包含成功/失败状态、可外跳链接（仅成功时）、可读文案键、错误码。
- **外跳结果**：包含“已请求打开支付宝”“支付宝不可访问”“支付码无效”“外跳失败”等状态、文案键、错误码。
- **回读事件**：包含支付意图摘要与离开时长；只表示“用户已返回”，不表示支付成功。
- **诊断结果**：包含支付宝可访问性、scheme 探测结果、最近一次自检/回读状态；仅 debug 构建可见。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 链接构建自检覆盖合法支付码、完整二维码 URL、空值、空白、控制字符和 URL 分隔符；所有用例 100% 通过，合法用例逐字符匹配 RN 基线。
- **SC-002**: 在已安装支付宝的真机上，从调试自检入口触发外跳后 3 秒内打开支付宝；在未安装支付宝的设备上，1 秒内出现“未检测到支付宝”的可读提示，应用崩溃次数为 0。
- **SC-003**: 存在有效期内的待回读状态时，应用回到前台后 2 秒内订阅方收到恰好一次事件；无状态、过期状态和进程重启场景下事件数为 0。
- **SC-004**: 完成一次“外跳 → 返回”后检索日志，支付码、二维码 URL、Cookie、学号、API Key 的出现次数均为 0。
- **SC-005**: `devecocli build` 与 `arkts_check` 通过，新增代码不引入 ArkTS error；既有构建基线不回退。
- **SC-006**: 支付基础设施与调试自检入口中不存在“支付成功”“充值成功”等结论性文案；只出现“已请求打开支付宝”“未确认支付结果”等中性文案。
- **SC-007**: release 构建中调试自检入口不可见，且无法通过正常导航到达。

## Assumptions

- 设备上的支付宝鸿蒙版至少注册 `alipayqr` 或 `alipays` 之一；具体可用性以真机探测为准。
- 支付码由电费、校园卡、体育子系统服务从各自上游获取；本特性不负责发起充值、下单或查询支付码。
- 待回读状态仅保存在进程内存；应用被杀后不补发事件，页面重新加载时按正常流程刷新余额/记录。
- `EntryAbility.onForeground` 能可靠覆盖“从支付宝返回 CampusOS”的场景；普通前台恢复由“是否存在待回读状态”过滤。
- 真实设备验收允许使用仅 debug 可见的支付通道自检入口，不将其视为各子系统的充值/下单 UI。
- 支付码、二维码 URL 和金额明文不属于可写入日志或持久化的数据。
- 三个子系统的页面会在收到回读事件后自行调用各自服务刷新数据；本特性不直接查询余额或流水。

## Open Questions

- 无未决问题。已确认：允许新增仅 debug 可见的支付通道自检入口；待回读状态仅内存保存，不跨进程持久化。
